## 一、目标

把 Claude Code 的 agent 工作方式改成两套互不干扰的模式：

1. **普通模式（原版）**：不进入工作流时，主会话保持原版提示词、原版工具、原版行为。除 `Workflow` 被禁用外，其它功能全部保留。
2. **工作流模式**：用户显式启动 workflow 后，任务在独立代理上下文里执行。索引层和管线层各自拥有完全不同的系统提示词与工具白名单。

一句话：**不进入 = 原版；进入 = 另一套提示词 + 另一套工具权限。入口由用户显式触发。**

落点：正常配置 `D:/claude-code/data/` 只保留唯一入口（`commands/wf.md`）和 `Workflow` 禁用；wf 资产整体放在独立配置 `D:/claude-code/workflow/wf-mode/`，通过独立进程加载。

```text
  （已落地）
```

## 五、索引层（决策级管线）

### 5.1 定位

索引层不是 Router，它本身就是一条管线，属于**决策级管线**：

- 输入：用户任务文本；
- 输出：`{status, pipeline, slots, deliverable, acceptance, excluded}` 或 `{status: needs_clarification, question, options}` 或 `{status: out_of_domain, reason}`；
- 工具按它自己的需要声明，不预先锁死为 Skill-only。（已完成设计）

### 5.2 规范内容

索引规范文件包含：

1. 三条管线的静态分流表：触发信号、不适用条件、交付物；
2. 任务特征提取；
3. 唯一匹配规则：先看交付物，再看动作词；两条都像必须澄清；
4. 槽位规则；
5. 计划格式；
6. 澄清条件；
7. 信息搜集域硬边界：先找现成资料/项目，不进入实现、不造轮子；
8. 输出 schema 的纯文字描述；
9. 自检清单。

（已完成：按 A 方案内嵌）

### 5.3 输出方式

- 不使用 workflow 的 `schema` 选项。实测：受限工具代理 + schema 会让 workflow 直接失败。（已完成实测）
- 改为要求代理只输出纯 JSON，由 workflow 脚本解析。（已落地）

## 十二、skill 注册实测结论与方案选择

### 12.1 实测结果

| 验证项 | 结果 |
|---|---|
| `skills:` 列表写法 | 能解析 |
| `skills:` 标量写法 | 能解析 |
| `skills:` 是否预加载内容 | **能**，但前提是该 agent 的 `tools` 里必须有 `Skill` |
| 未写 `skills:` 的 agent | 不会预加载；但仍可通过 `Skill` 工具**调用任何全局已注册 skill** |
| `disable-model-invocation: true` | 主会话看不到（init `skills` 列表不出现），但**同时阻止所有 agent 的 Skill 调用和 `skills:` 预加载** |
| `skills:` 绑定注册目录之外的路径/文件 | **不支持**，只能绑定已注册的 skill 名 |
| 主会话技能过滤设置 | 尝试 13 个 `settings.json` 候选键均无效 |
| `skillOverrides`（`off` / `name-only` / `user-invocable-only`） | CLI 二进制存在；**GUI 引擎实测无效**（用户 settings 与 `--settings` 均不生效） |

### 12.2 结论

这个构建里，**“全局 skill 注册”和“只让某个 agent 拥有、主会话和其它 agent 看不到”是互斥的**：

- 要预加载 → 必须全局可调用 → 主会话会看到；
- 要隐藏 → `disable-model-invocation` → 连预加载一起失效；
- 要路径绑定 → 不支持。

所以原生 Skill 机制**无法满足**你要求的注册期隔离。

### 12.3 三个可选方案

| 方案 | 做法 | 隔离程度 | 代价 |
|---|---|---|---|
| **A（推荐）正文内嵌** | 把规范文本在装配时写进对应 agent 的正文；规范源文件只作维护源 | 100%：主会话和其它 agent 都拿不到 | 规范更新时要重新生成/粘贴 agent 正文 |
| **B 独占规范文件** | 规范放在 `workflow/wf-mode/workflow/specs/<layer>/SKILL.md`；agent 用受限 `Read` 只读自己那份 | 100%（agent hook 限定路径） | 索引/管线 agent 多一个 `Read` 工具；多一次读取动作 |
| **C 原生全局 skill** | 全局注册 + `skills:` 预加载 + agent hook 限定 Skill 名 | 行为上接近，但主会话技能列表会看到这些 skill | 违反“不经过原版” |

### 12.4 方案确认

- **采用 A（正文内嵌）**：规范在装配时写进对应 agent 正文；规范源文件只作维护源。
- 多份强制规范：在同一个 agent 正文里按小节内嵌，进入即全部加载。
- 索引层、管线层的规范都**不进全局 skill 注册**，普通模式的技能列表保持原样。
- 不使用 B 的 `Read` 加载；不使用 C 的全局注册。

### 12.5 可选规范目录槽位（后续扩展，v1 不实现）

强制规范用 A 内嵌。**可选/备选规范**预留一个独立槽位，v1 只写目录，不实现加载器。

设计：

```text
agent 正文：
  ## 强制规范（内嵌）
  ...
  ## 可选规范目录（只有名字 + 适用条件，不含正文）
  - wf-spec-xxx：什么时候用
  - wf-spec-yyy：什么时候用

需要时通过“规范目录服务”按名字加载：
  list_specs()  -> 返回可用规范清单
  load_spec(name) -> 返回该规范正文
```

约束：

- 服务以 **MCP 工具**形式提供，而不是 Read 直接读文件。后续优先选 GitHub 上现成的 MCP 项目，不自造。
- 每个 agent 的工具白名单只给它需要的服务工具；agent 级 hook 按 `agent_type` 校验 `load_spec` 的名字 allowlist。
- 不在 agent 白名单里的规范名，加载被拒绝。
- 记忆/检索类插件（mem0/OpenMemory、Letta/MemGPT、Basic Memory、Memory Bank MCP、Cognee、Zep）只作为后续“语义推荐备选规范”的实验选项，不作为强制规范，也不进 v1。
- 原生 `MCP skill（server:skill）`、条件 skill、`skillOverrides` 在 GUI 引擎里未验证/无效，不依赖。

v1 状态：（只写目录槽位，不实现服务）

### 12.6 后续扩展：统一能力网关（v1 不实现）
